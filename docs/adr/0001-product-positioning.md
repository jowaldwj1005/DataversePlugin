# ADR-0001: Product positioning — environment-scoped Agent-first developer Workspace

## Context

We are rewriting the Dataverse Toolkit Chrome extension on a greenfield branch; the existing build (described by the owner as "heavily vibe-coded, loosely wired together") remains on `main` as reference until cutover. Phase 1 must lock in *what the product is*, before Phase 2 triages features, Phase 3 picks a UX model, and Phase 4 picks an architecture.

The market for Dataverse developer tooling is shaped by three incumbents:

- **XrmToolBox** — Windows-only desktop, ~hundreds of community plugins via a gallery. Loved for its breadth; chronically painful for slow startup, version skew, abandoned plugins, and Windows-lock-in.
- **Level Up** — Chrome extension that overlays controls onto the host model-driven app page. Form-scoped (one record at a time). Loved for one-click contextual actions on the page you're already on.
- **make.powerapps.com** — Microsoft's official authoring surface. GUI-heavy, single-table-at-a-time, slow round-trip for Solution-scale work.

Adjacent to this: **Power Platform CLI** (`pac`) covers headless ALM; **PPAC** covers env administration; **Microsoft's Dataverse Skills** (for Claude Code and Copilot, shipped May 2026) target the headless agentic dev loop. The AI-native Dataverse-developer category is forming *now*.

The owner is a senior Power Platform / D365 developer. Phase 1 grilling clarified the job-to-be-done: **interrogate and shape a live Dataverse Environment in a tight, conversational loop**. Concretely — authoring tables and relationships at Solution scale; inspecting schema with the live data alongside it; auditing what AI agents have done against the Environment; agentically generating forms/views; testing Web API calls before they land in custom code or Power Automate. All four stated use cases are *primary*, not ranked; further use cases are expected to emerge over time. Release engineering — solution export/import, environment promotion, CI/CD — is explicitly **not** the job; it stays with `pac`, pipelines, and PPAC.

## Decision

The product is **an environment-scoped, multi-Module developer Workspace for Dataverse, designed end-to-end for human-Agent collaboration**, delivered as a Chrome side panel. Every Module is an *Agent-first UI*: jointly operable by a human at the keyboard and by the Agent through Tools. The intent is to be a showcase of what excellent human-Agent interaction looks like in a developer tool — *not* a chat box bolted onto a workbench.

- **Who it serves.** The classical Power Platform / Dataverse developer — schema designer, query author, data-model maintainer, Web API consumer. The Agent collaborates with them across every Module; it is not their identity, but it is central to how the product works.
- **Verbs.** *Inspect, query, author, test, migrate* — against a live Environment, with the Agent participating in every verb.
- **Unit of identity.** The connected Environment. The Workspace recontextualizes when the host page navigates to a different Environment; switching Environments switches everything (auth, schema cache, selection, Agent conversation).
- **Agent-first UI everywhere.** Every Module — including the deterministic, direct-manipulation ones (Query, Request Builder, ERD, Form, Bulk Ops) — exposes its state via the Module Bridge and exposes its meaningful actions as Agent Tools. Agent-first is a design principle, not a synonym for "chat" — most Agent-first surfaces in this product are non-chat (tables, graphs, code editors, bulk grids with filters).
- **Three interaction modes, not two.** The simple binary "Agent-driven vs direct-manipulation" is wrong. Capabilities live in one of three modes: *Agent-only* (invoked only through the Agent, may still have a UI for visualization or confirmation — e.g. *add column*); *UI-led, Agent-augmented* (primary direct-manipulation surface, Agent can also drive — e.g. Query, Request Builder, ERD, Form, Explorer); *Agent-led, UI-augmented* (Agent orchestrates a multi-step flow, UI shows diffs/progress and accepts human interventions — e.g. Solution-scale Authoring, "CMT on crack"). Tagging each Module / Tool with its mode is a Phase 2 deliverable.
- **Authoring is Agent-driven across all three modes — never WYSIWYG.** Single-column or single-relationship adds are *Agent-only* Tools with possible UI confirmation. Solution-scale Authoring is *Agent-led, UI-augmented*. Agent-driven *generation* of forms and views is in scope (one-shot create forms across many entities). A click-by-click WYSIWYG form / view / schema *editor* is **not** — make.powerapps.com remains the canonical visual designer. Authoring requires the Agent to be configured (BYOK set).
- **Bulk Ops is a flagship Module, repositioned, not cut.** Modeled on Microsoft's Configuration Migration Tool (CMT) but with Agent-driven filtering, mapping suggestions, schema-aware translation across Environments, and Solution-scale awareness. *"CMT but on crack."* The existing 5K-line wizard implementation is replaced.
- **Direct-manipulation Modules stay, reimagined.** Query / FetchXML, Request Builder, ERD, Form inspector, and Bulk Ops cover work make.powerapps.com does poorly or not at all (multi-syntax codegen, Web API testing, joint schema-plus-data inspection, config migration). They remain primary, human-first surfaces — but reimagined Agent-first under the hood.
- **Extensibility mechanism.** Agent + Skills, **not** a plugin gallery. New capabilities arrive as Skills (markdown plus Tool links, persisted in Dataverse) and tool-registry entries that ship with the product. When make.powerapps.com covers a workflow we don't, the answer is "author a new Skill", not "build a new UI tab". No third-party plugin SDK, no gallery moderation, no version skew.
- **Differentiation.**
  - vs. **XrmToolBox**: Mac/Linux parity, browser-delivered (no install), Agent-first across every Module, shared state across Modules (XrmToolBox plugins are isolated windows that re-authenticate per tool, and the Agent is absent).
  - vs. **Level Up**: multi-Module Workspace, not form-scoped; complements rather than competes — Level Up's God Mode manipulates the host page DOM, and we do not try to replicate that surface.
  - vs. **make.powerapps.com**: a broad substitute for the developer-facing surfaces — tables, columns, relationships, views, security roles, forms — but reached through Agent-driven Authoring rather than the make GUIs. Solution-scale Authoring (multi-table in one flow), joint schema + data view, and Skill-mediated reusable workflows. We accept that we won't cover every workflow perfectly; the path to coverage is to author a new Skill. make's visual form designer and canvas-app designer remain canonical for those specific jobs.
  - vs. **Microsoft Configuration Migration Tool (CMT)**: Agent-driven filters and mapping suggestions; runs against the live Environment instead of a downloaded XML; Solution- and schema-aware; browser-delivered (no Windows desktop install); the headline use case for our Bulk Ops Module. "CMT but on crack."
  - vs. **Microsoft Dataverse Skills (Claude Code / Copilot)**: a stateful, visual Workspace where the Agent and the human share every UI surface — they target the headless IDE/CLI dev loop. Different surface, complementary positioning.

## Alternatives considered and rejected

- **"AI-native session workspace"** (the Phase 1 straw-man). Rejected, but for a more subtle reason than first reading: "AI-native" is a buzzword and "session" is the wrong unit. We use *Agent-first* instead — which is a specific design principle (every UI is jointly human + Agent operable, with both non-chatbot surfaces and deterministic controls), not just a synonym for "has AI in it". The Agent is central, the framing is not.
- **"Optional agent on the side"** (the over-correction one revision back). Rejected. Some Modules still function without an Agent configured, but the *design* is never "agent on the side" — every UI is built for joint human + Agent operation, even when no AI key is set. Standalone use is a narrower mode of the same UI, not a different UI.
- **"Chatbot-first UX"** (chat is the primary surface; Modules render as visualisations of Agent output). Rejected. The product is *Agent-first* but not *chatbot-first* — most Agent-first UIs in this product are non-chat surfaces (tables, graphs, forms, bulk grids with filters). Agent Chat is one Module among many, not the shell. Excellence at human-Agent interaction means making the non-chat surfaces jointly operable, not collapsing everything into a text input. (Detailed UX shape — exact placement of Agent Chat, command palette, Module navigation — deferred to ADR-0003.)
- **Session as the unit of work.** Rejected. The owner's work spans seconds (one Web API call) to weeks (a Solution's data model). "Session" implies an ephemeral, time-boxed unit that doesn't match reality. The unit is the Environment — the persistent connection that everything else hangs off.
- **XrmToolBox-style plugin gallery.** Rejected. The gallery model is XrmToolBox's biggest pain (version skew, abandoned plugins, slow startup, Windows-only). Skills as markdown-in-Dataverse are simpler, versioned with the org, shared via the same mechanism the rest of the user's customizations are.
- **Read-only Investigation Workspace** (route all writes to make.powerapps.com). Rejected. The owner's most-frequent use case is Authoring whole data models at Solution scale; excluding Authoring would mean the user keeps make.powerapps.com as their primary tool and our Workspace becomes a secondary read lens.
- **Direct-manipulation form / view / schema designers.** Rejected on purpose, not just for forms. We will not build click-by-click WYSIWYG designers for any Authoring surface. The value-add is *Agent-driven Authoring + reusable Skills*, not a competing GUI. A form change is "ask the Agent" → Skill runs → applied to Dataverse. Imperfect coverage is acceptable; the gap closes by authoring a Skill, not by building another tab. make.powerapps.com remains the visual designer for jobs that genuinely need one. Note: this is distinct from rejecting *direct-manipulation Modules* — we keep those for Query, Request Builder, ERD, Form inspector, and Bulk Ops; the rejection is specifically of WYSIWYG schema/form editors.
- **Cutting Bulk Ops** (the Phase-0 audit recommendation). Rejected. The Phase-0 verdict was based on the current implementation's 5K-line wizard-stepper tangle, not the underlying use case. Configuration Migration between Environments is a real, high-value job that Microsoft's CMT does badly (Windows-only desktop wizard, no schema awareness, XML-only). Repositioned as flagship Module — *"CMT but on crack"* — with Agent-driven filters and mapping suggestions.
- **Multi-Environment Workspace** (many Environments side-by-side, "explore Solution X in env A, apply to env B"). **Parked, not rejected.** The current auth model is per-Chrome-tab session-cookie at the org origin; cross-Environment workflows require either multiple Chrome tabs or a different auth path. Acknowledged as a future ambition; out of MVP scope.
- **Auditing external AI agents** (Foundry, Copilot Studio, third-party) **as a primary use case.** Rejected. *Investigation* in this product covers (a) generic inspection of Dataverse data — which incidentally includes the audit-log table among many — and (b) auditing the Workspace's own Agent (Claude-Code-style transcript of Tool calls, decisions, mutations; possibly extended). External-agent observability is someone else's product.

## Consequences

**Commits us to:**

- **Every Module is designed Agent-first from day one.** Each Module surfaces its full state via the Module Bridge and exposes every meaningful user action as an Agent Tool. There are no human-only affordances. This is a build-time constraint on every Module, not a polish step.
- **Perfect Agent-first UIs know where AI stops.** Some interactions are inherently better as deterministic visual operations — browsing the entity list, scrolling fields with their types and option-set values, picking a relationship from a graph, executing a saved query with one click. We do not route these through the Agent and we do not require chatting to do them. Visual, deterministic primacy for navigation, inspection, and well-understood operations; Agent collaboration for synthesis, multi-step flows, and Authoring. Getting the boundary right is the design challenge.
- **Direct-manipulation Modules must be fully functional without the Agent configured.** Query / FetchXML, Request Builder, ERD, Form inspector, and Bulk Ops each support their core job standalone — no BYOK required. A user who refuses to configure BYOK gets a smaller but uncompromised product; the UIs are the same, the Agent just isn't there. The Agent's absence is felt as missing collaboration, not missing buttons.
- **Authoring is a first-class, Agent-driven capability in the rewrite** — not a v2, not a click-UI. It serves the owner's most-frequent use case and is the differentiator vs. make.powerapps.com. Authoring is the one job that *does* require an Agent.
- **Bulk Ops is rebuilt, not cut.** The existing wizard-stepper code is replaced. The new surface is the "CMT on crack" Module — Configuration-Migration-style record movement with Agent filtering, mapping suggestions, schema awareness, and Solution-scale awareness. A flagship of the human-Agent UX showcase.
- **Human-Agent interaction quality is the product's defining quality bar.** The owner has explicitly asked for the Workspace to be a *showcase* of excellent human-Agent UX in a developer tool. This drives investment in: shared selection state between Modules and the Agent's context; Agent action previewing / dry-running before mutation; non-chat surfaces as first-class Agent targets; deterministic controls remaining predictable and AI-free when that is what the task needs.
- **The Agent + Skills mechanism is load-bearing** for both Authoring and extensibility. Authoring without an Agent is unsupported; future Modules / workflows arrive as Skills rather than new UI tabs by default. Skill-authoring UX matters as much as Agent chat UX.
- **The Workspace Agent is observable and auditable.** Tool calls, decisions, and mutations are visible to the user in Claude-Code-style transcripts — with room to go further (record-level diffs, replay, "what changed since I asked"). This is a first-class capability, not a debug log.
- One Environment at a time. The Workspace, schema cache, and Agent context all key on a single Environment. Cross-Environment workflows are deliberately deferred.
- Mac/Linux parity is a permanent moat. No code paths that depend on Windows. (Being on Chrome MV3, this is mostly free — but we will not regress.)
- BYOK is permanent. Users provide their own AI provider credentials; we never operate a backend that brokers AI calls.

**Forecloses:**

- We are not building an installable third-party plugin platform. No plugin SDK, no gallery, no third-party signing.
- We are not building a release / ALM tool. No solution packaging, no Environment promotion, no CI/CD integration. Those remain with `pac` and pipelines.
- We are not building a citizen-developer surface. The product assumes the user can read schema names, GUIDs, FetchXML, OData, and Web API JSON. make.powerapps.com remains the no-code path.
- We are not building visual designers. No form designer, no view designer, no canvas-app designer, no business-process flow designer. When a job needs one, the user opens make.powerapps.com.
- We do not host AI infrastructure for users. No backend-brokered AI, no shared model deployments, no usage billing on our side.
